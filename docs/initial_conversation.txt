### 4. The View System

The view system is the core product differentiator. All views render the **same underlying comment data** through different query and presentation layers.

#### 4.1 Thread View (Default)

**Purpose:** Chronological discussion as it happened, with context preservation.

**Implementation:**
- Standard nested comment tree, indented by depth
- **Compressed Ancestor Trail**: A sticky bar at the top of the viewport showing the chain of parent comments when the user has scrolled deep into a thread. Each ancestor displays: author name, stance badge, first ~80 characters of content, and is clickable to scroll/expand in place.
- Ancestor trail renders from `Comment.ancestorPath` (materialized path array)
- Collapse/expand controls per subtree
- Comments beyond depth 6 flatten visually (no further indentation) but maintain logical nesting
- No pagination to new pages — infinite scroll with virtual windowing (`react-window` or `tanstack-virtual`) for performance

**Key query:**
```sql
SELECT c.*, u.username, u.avatarUrl, ds.declaredStance, ds.algorithmicLean
FROM comments c
JOIN users u ON c.authorId = u.id
LEFT JOIN debate_stances ds ON ds.debateId = c.debateId AND ds.userId = c.authorId
WHERE c.debateId = :debateId
ORDER BY c.createdAt ASC
```

#### 4.2 Sides View

**Purpose:** Discovery surface — see the strongest arguments for each side without digging.

**Layout:**
- Desktop: Two columns, Side A (left) and Side B (right), with a toggleable "Neutral" column or inline section
- Mobile: Tab bar with three tabs [Side A | Side B | Neutral]
- Each column shows comments filtered by `stanceSide`, sorted by computed score (weighted vote aggregate)
- Each comment card shows: author, stance badge, truncated content (~200 chars), vote breakdown by reason, and a "View in Context" button
- "View in Context" navigates to Thread View, scrolls to the comment, and highlights it with the ancestor trail visible

**Key query:**
```sql
SELECT c.*, 
  COUNT(v.id) FILTER (WHERE v.direction = 'up') as upvotes,
  COUNT(v.id) FILTER (WHERE v.direction = 'down') as downvotes,
  -- Weighted score: changed_my_mind votes count 3x, well_sourced 2x, etc.
  SUM(CASE 
    WHEN v.direction = 'up' AND v.reason = 'changed_my_mind' THEN 3 * v.weight
    WHEN v.direction = 'up' AND v.reason = 'well_sourced' THEN 2 * v.weight
    WHEN v.direction = 'up' THEN 1 * v.weight
    WHEN v.direction = 'down' THEN -1 * v.weight
    ELSE 0
  END) as weighted_score
FROM comments c
LEFT JOIN votes v ON v.commentId = c.id
WHERE c.debateId = :debateId AND c.stanceSide = :side
GROUP BY c.id
ORDER BY weighted_score DESC
LIMIT :pageSize OFFSET :offset
```

*This query result is cached in Redis with a TTL of ~60 seconds, invalidated on new votes.*

#### 4.3 Best Exchanges View

**Purpose:** Surface the strongest back-and-forth dialogues — cross-examinations where both sides performed well.

**Algorithm:**
1. Find all comment pairs where:
   - Comment B is a direct reply to Comment A
   - A and B have opposing `stanceSide` values
   - Both have a `weighted_score` above a minimum threshold (e.g., 75th percentile for the debate)
2. Score each pair: `pair_score = min(A.score, B.score) * 2 + max(A.score, B.score)` — this formula favors balanced exchanges over one-sided blowouts
3. Extend to chains: if B's reply C also scores well and opposes B, present as a 3-part exchange
4. Future enhancement: track read-through rate (did users who saw comment A also read comment B?) to weight by retention as Gemini's reviewer suggested

**Layout:**
- Cards showing paired/chained comments side by side (desktop) or stacked with visual connectors (mobile)
- Each card links to full thread context
- Sortable by: pair score, recency, number of stance shifts triggered

#### 4.4 Neutral Verdict View

**Purpose:** What do the self-declared neutral observers think? The platform's most credible signal.

**Layout:**
- Hero section: large tally bar showing Neutral users' verdict votes (Side A winning / Side B winning / Draw), updated via SSE
- Below: comments that Neutral users pinned as decisive, sorted by pin count
- Stats panel: total neutral voters, percentage of neutrals whose algorithmic lean matches their declared neutral stance (credibility indicator), stance shift history among neutrals
- Filter: "Verified Neutrals only" — users whose `algorithmicLean` is `neutral` or `mixed` with `leanConfidence < 0.3`

#### 4.5 Analytics View (Phase 3)

**Purpose:** Dashboard for debate-level and platform-level metrics.

**Metrics displayed:**
- Stance distribution over time (line chart)
- Vote reason breakdown (what types of arguments are landing?)
- Persuasion leaderboard (users with highest `changed_my_mind` received)
- Argument taxonomy distribution (are economic or moral arguments dominating?)
- Cohort snapshots (periodic snapshots of debate state for time-series analysis)
- Engagement depth histogram (how deep do threads go before engagement drops?)

### 5. Computed Systems (Background Jobs)

These run asynchronously, not on the request path.

#### 5.1 Algorithmic Stance Detection

**Trigger:** Runs every N minutes per active debate, or on significant vote/comment events.

**Logic:**
```
For each user in debate:
  comments_side_a = count of their comments with stanceSide = side_a
  comments_side_b = count of their comments with stanceSide = side_b
  votes_for_a = count of upvotes they gave to side_a comments
  votes_for_b = count of upvotes they gave to side_b comments
  
  total = comments_side_a + comments_side_b + votes_for_a + votes_for_b
  if total < 5: algorithmicLean = 'mixed', confidence = 0
  else:
    lean_score = (a_signals - b_signals) / total  // -1 to +1
    if lean_score > 0.4: algorithmicLean = 'side_a'
    elif lean_score < -0.4: algorithmicLean = 'side_b'
    else: algorithmicLean = 'mixed'
    confidence = abs(lean_score)
```

Display rule: Only show "Leans [Side]" badge when `declaredStance` is `neutral` AND `confidence > 0.5`. This avoids noisy indicators.

#### 5.2 Score Computation

Precompute and cache in Redis:
- Per-comment weighted scores (for Sides View sorting)
- Per-pair exchange scores (for Best Exchanges View)
- Per-debate verdict tallies segmented by voter stance
- Per-user reputation and persuasion scores

#### 5.3 Engagement Fingerprinting (Phase 3)

For each user, compute a profile vector stored as JSONB:
```json
{
  "debatesEngaged": 12,
  "avgStance": 0.3,           // -1 to 1 across all debates
  "stanceConsistency": 0.7,   // how often same-leaning across topics
  "mindChangeRate": 0.15,     // proportion of debates where stance shifted
  "argumentStyleWeights": {
    "empirical": 0.4,
    "moral": 0.2,
    "economic": 0.3,
    "anecdotal": 0.1
  },
  "engagementDepth": "deep",  // shallow/moderate/deep
  "persuasionScore": 42,
  "upvoteReasonProfile": {
    "well_reasoned": 0.5,
    "well_sourced": 0.3,
    "changed_my_mind": 0.1,
    "well_written": 0.1
  }
}
```

### 6. Moderation System

#### 6.1 Automated Quarantine

Comments are auto-quarantined (collapsed with warning label, not deleted) when:
- Toxicity score exceeds threshold (use Perspective API or similar)
- Rapid accumulation of `uncivil` downvotes (e.g., 5+ in first 10 minutes)
- Account is in `new` trust tier and comment matches spam patterns

Quarantined comments display: "This comment has been collapsed due to community flags. [Click to read] [Appeal]"

The comment's votes are excluded from computed rankings while quarantined but the content is preserved for transparency.

#### 6.2 Trust Tiers

| Tier | Threshold | Privileges |
|---|---|---|
| `new` | Account < 7 days or < 5 comments | Votes don't count toward Verdict; rate-limited posting |
| `established` | 7+ days AND 10+ comments with net positive score | Full voting weight; can tag argument taxonomy |
| `trusted` | 30+ days AND high reputation score AND low quarantine rate | Can vote on moderation appeals; 1.5x vote weight in analytics |
| `moderator` | Appointed | Can resolve quarantine appeals, lock threads, edit debate metadata |
| `admin` | Platform owner | Full access |

#### 6.3 Burden of Proof Mechanic

When a comment accumulates 3+ `misleading_unsourced` downvotes:
1. System pins a "Citation Requested" notice to the comment
2. Author is notified and can add a source URL/citation
3. If citation is provided and receives 3+ `well_sourced` upvotes from other users, the `misleading_unsourced` downvotes are neutralized
4. If no citation after 72 hours, the `misleading_unsourced` downvotes remain at full weight and the comment is labeled "Unsupported Claim"

# Agora — Federation & Multi-Site Architecture

## Spec Addendum v1.0

---

## 1. Problem Statement

Agora is designed to be deployed as independent instances across different niches (e.g., `climate.agora.example`, `policy.agora.example`, `tech-ethics.agora.example`). Each instance is operated by a different admin, potentially on different infrastructure. However, users and admins should be able to **optionally** link these instances together, creating a network effect similar to Stack Exchange or Discord — but without requiring a single centralized operator to control all sites.

### Design Goals

1. **Each site works fully standalone.** No site depends on the Hub or any other site to function. If the Hub goes down, individual sites keep running — they just lose cross-site features.
2. **Users opt into linking.** Cross-site profile visibility is always user-controlled. A user can participate on `climate.agora.example` without anyone on `tech-ethics.agora.example` knowing they exist — unless they choose otherwise.
3. **Admins opt into networking.** Site admins decide which other sites (if any) their instance connects to. A site can exist in multiple networks or none.
4. **Reputation is portable but contextual.** A user's cross-site reputation provides social proof, but each site's local reputation remains the primary signal. You don't get to dominate a new community just because you're well-known elsewhere.
5. **No single point of failure.** The architecture should degrade gracefully. Cross-site features are enhancements, not dependencies.

---

## 2. Architecture: Hub and Spoke

```
                    ┌─────────────────────┐
                    │    Agora Hub         │
                    │  (Identity + Index)  │
                    │                      │
                    │  - User identity     │
                    │  - SSO tokens        │
                    │  - Profile links     │
                    │  - Reputation index  │
                    │  - Site registry     │
                    └──────┬──────────────┘
                           │
              ┌────────────┼────────────┐
              │            │            │
        ┌─────▼──┐   ┌────▼───┐   ┌───▼─────┐
        │ Site A  │   │ Site B │   │ Site C  │
        │climate  │   │policy  │   │tech     │
        │         │   │        │   │ethics   │
        │Own DB   │   │Own DB  │   │Own DB   │
        │Own admin│   │Own admin│  │Own admin│
        └─────────┘   └────────┘   └─────────┘
```

### 2.1 The Hub

The Hub is a lightweight service with a narrow, focused responsibility: **identity and cross-site indexing**. It does NOT store debate content, comments, or votes. It stores:

- **Global User Identities** — a universal account that can be linked to site-local accounts
- **Profile Link Registry** — which site-local accounts belong to the same person (user-controlled)
- **Aggregated Reputation Snapshots** — periodically synced summaries from each site (not raw data)
- **Site Registry** — metadata about participating sites (name, URL, niche, admin contact, trust status)
- **SSO Token Issuance** — OpenID Connect provider for single sign-on across sites

### 2.2 The Spoke (Each Site Instance)

Each Agora site instance is the full platform as described in the main SPEC.md. It adds:

- An **SSO client** that can authenticate against the Hub (in addition to local auth)
- A **Federation API** for receiving/sending reputation snapshots and profile lookups
- **Local-first storage** — all content lives on the site's own database; nothing depends on the Hub

## 4. Authentication Flow

### 4.1 Single Sign-On (SSO)

The Hub acts as an **OpenID Connect (OIDC) Provider**. Each site is an OIDC client.

**First visit to a new site (user already has Hub account):**

```
User visits Site B → clicks "Sign in with Agora" →
  Redirected to Hub OIDC authorize endpoint →
    Hub checks session (or asks user to log in) →
      Hub returns authorization code →
        Site B exchanges code for ID token + access token →
          Site B creates local account, links to Hub ID via FederatedIdentity →
            User is logged in on Site B
```

**First visit ever (no Hub account):**

```
User visits Site A → creates a local account (email/password or OAuth) →
  Optionally: "Link to Agora Network" button in settings →
    Redirected to Hub → creates Hub account (or links to existing) →
      Returns to Site A with link established
```

**Key principle:** Users can always create a purely local account. Hub linking is opt-in, prompted but never forced.

### 4.2 Hub OIDC Configuration

```
Hub OIDC Endpoints:
  /.well-known/openid-configuration
  /oauth/authorize
  /oauth/token
  /oauth/userinfo
  /oauth/jwks

Claims returned in ID token:
  sub:          Hub user UUID
  email:        verified email
  name:         display name
  picture:      avatar URL
  agora_sites:  [list of site slugs where user has linked profiles]
                (only included if user's profileVisibility allows)
```

### 4.3 Site Registration with Hub

```
Site admin → Hub admin panel → "Register New Site"
  Provides: site name, URL, admin email, niche description
  Receives: client_id, client_secret (for OIDC), api_key (for Federation API)
  Status: pending → verified (after Hub admin review or automated domain verification)
```

```
GET    /federation/sites
  Returns: Registry of all verified sites in the network

POST   /federation/verify-link
  Body: { hubUserId, siteLocalUserId }
  Purpose: Confirm a profile link is valid (called during SSO)
```

### 5.2 Site API (called by Hub or other Sites)

```
# Hub → Site communication (or Site → Site for direct federation)
# Authenticated with mutual API keys

GET    /api/federation/user/:localUserId/reputation
  Returns: This site's reputation snapshot for the user

GET    /api/federation/user/:localUserId/highlights
  Returns: Top 5 comments by this user on this site
  (truncated to 200 chars each, with debate title and link)
  Purpose: Enables "See their best arguments on [Site Name]" feature

GET    /api/federation/stats
  Returns: Site-level stats (total users, total debates,
           active debates, avg engagement)
  Purpose: Hub displays network-wide statistics
```

### 5.3 Sync Protocol

Reputation syncing is **eventually consistent** and **site-initiated**:

1. Each site runs a background job (e.g., every 6 hours) that computes reputation snapshots for all users with a `FederatedIdentity`
2. Site pushes snapshots to Hub via `POST /federation/sync-reputation`
3. Hub aggregates across all sites and updates `HubUser.globalReputationScore`
4. When a site needs to display cross-site reputation (e.g., on a user's profile card), it calls `GET /federation/user/:id/cross-site-reputation` and caches the result locally in `CrossSiteReputation` with a TTL of 1 hour
5. If the Hub is unreachable, the site displays the last cached value (or nothing, for new users)

**This means no real-time cross-site dependency.** Reputation data is always hours old at most, which is acceptable for a trust signal.

## 8. Reputation Aggregation Algorithm

The global reputation score is not a simple sum. It uses a **diminishing returns** model to prevent any single site from dominating, and weights by site credibility.

```python
def compute_global_reputation(snapshots: list[ReputationSnapshot]) -> float:
    """
    snapshots: one per linked site, sorted by localReputationScore DESC
    """
    global_score = 0
    
    for i, snap in enumerate(snapshots):
        # Diminishing weight: first site counts most,
        # each additional site adds less
        # Site 1: weight 1.0, Site 2: 0.6, Site 3: 0.4, Site 4: 0.3 ...
        position_weight = 1.0 / (1 + 0.5 * i)
        
        # Site trust multiplier (verified sites count more)
        site_trust = {
            'verified': 1.0,
            'pending': 0.5,
            'suspended': 0.0
        }[snap.site.trustStatus]
        
        # Engagement depth multiplier
        # (a user with 100 comments on a site is more credible
        #  than one with 2 comments)
        depth = min(snap.debatesParticipated / 10, 1.0)  # caps at 10 debates
        
        weighted = snap.localReputationScore * position_weight * site_trust * depth
        global_score += weighted
    
    return round(global_score, 1)
```

**Why diminishing returns:** Without this, a user could inflate their global score by creating accounts on many low-activity sites and earning easy reputation. The diminishing model means your strongest community contribution matters most.

## 9. Privacy & Data Controls

### 9.1 User Controls

| Setting | Options | Default |
|---|---|---|
| Profile link visibility | Public / Mutual / Private | Private |
| Show cross-site reputation | Yes / No | Yes (if linked) |
| Show cross-site comment highlights | Yes / No | No |
| Allow network search to index my debates | Yes / No | Yes |
| Share engagement fingerprint across sites | Yes / No | No |

### 9.2 Data Residency Rules

- **Comment content, votes, and debate data NEVER leave the originating site's database.** The Hub only receives computed reputation snapshots (numbers and categories, not content).
- **Comment highlights** (truncated text shown on cross-site profiles) are only sent to the Hub if the user explicitly enables "Show cross-site comment highlights." Even then, only the first 200 characters of their top 5 comments are transmitted.
- **Engagement fingerprints** are never shared by default. If a user opts in, only the category weights (not raw data) are shared — e.g., `{"empirical": 0.4, "moral": 0.3}`, not the comments themselves.
- **Account deletion** propagates: deleting a Hub account triggers deletion requests to all linked sites via the Federation API. Each site removes the `FederatedIdentity` record. Local accounts can optionally be preserved (de-linked) or deleted, per the user's choice.

### 9.3 GDPR / Privacy Compliance

- Hub maintains a data processing agreement template for site admins
- All cross-site data transfers use the Federation API (auditable, rate-limited)
- Users can export all Hub data (profile links, reputation history) via a self-service portal
- Right to erasure: Hub deletion cascades to all linked sites within 72 hours

## 13. Security Considerations

### 13.1 Site-to-Hub Authentication

Every Federation API call from a site includes:
- `X-Agora-Site-Id` header (the site's registered UUID)
- `X-Agora-Signature` header (HMAC-SHA256 of request body using the site's API key)
- `X-Agora-Timestamp` header (request timestamp; reject if >5 minutes old to prevent replay attacks)

### 13.2 User Impersonation Prevention

When a site pushes a reputation snapshot for a user, the Hub verifies:
1. The `hubUserId` in the snapshot has an active `ProfileLink` to the requesting site
2. The `siteLocalUserId` in the `ProfileLink` matches what the site is reporting
3. Reputation values are within plausible bounds (rate limiting prevents a site from suddenly granting a user 999,999 reputation)

### 13.3 Rogue Site Mitigation

If a site is compromised or acting in bad faith:
- Hub admin can **suspend** the site, immediately excluding its data from all cross-site aggregations
- All `ReputationSnapshot` records from that site are quarantined (not deleted, in case of false alarm)
- Users with profiles linked to the suspended site see a notice: "One of your linked sites has been suspended. Your global reputation has been recalculated."
